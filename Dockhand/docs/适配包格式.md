# 适配包格式 v1

适配包是插件里唯一和"某个具体游戏"有关的东西。它是**纯数据**：四类 JSON + 一组图片，没有一行可执行代码。

设计目标只有一个：**换游戏不用改插件**。加一个游戏 = 加一个目录；改一个游戏 = 改一个目录里的 JSON。改完不需要碰 `engine/`，也不需要重新审插件。

---

## 一、目录结构

```
game_adapter/
└── <pack_id>/
    ├── manifest.json      包元信息
    ├── states.json        界面定义（界面 = 特征，不是位置）
    ├── goals.json         目标定义（目标 = 步骤序列）
    ├── skills.json        技能定义（技能 = 原子动作）
    └── templates/         模板图（可选，demo 包里有）
        ├── main_map.png
        └── ...
```

`<pack_id>` 必须匹配 `^[a-z][a-z0-9_]{0,47}$`：小写字母开头，只含小写字母、数字、下划线，最长 48 字符。

为什么要限制：这个 id 会出现在配置、命令、日志和 URL 里。带空格、大写、中文的名字在 JSON 里合法，但在命令行和配置文件里是持续的麻烦源。与其让每个人自己踩一次，不如在加载时就拒掉。

## 二、manifest.json

```json
{
  "pack_id": "demo",
  "name": "示例包（只读，不可运行）",
  "version": "1.0.0",
  "author": "shipctl",
  "demo": true,
  "entry_states": ["main_map"],
  "protocol_min": 2,
  "license": "MIT",
  "summary": "用于验证链路的示例包",
  "format_version": 1
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `pack_id` | 是 | 与目录名一致。不一致会被拒绝——两份 id 会让人不知道日志里说的是哪个 |
| `name` | 是 | 显示给人看的名字 |
| `version` | 是 | 包自己的版本，与插件版本无关 |
| `author` | 否 | 出了识别问题用户得知道找谁 |
| `demo` | 否 | `true` 表示只读示例包。**这是硬约束，不是标签**：`demo: true` 的包在任何情况下都不允许实跑 |
| `entry_states` | 否 | 进入游戏后可能落到的界面。用于判断"现在能不能开始" |
| `protocol_min` | 否 | 依赖的 agent 协议版本，默认 2 |
| `license` | 否 | 建议明确写。模板图涉及第三方素材时这一栏尤其重要 |
| `format_version` | 否 | 当前为 1。将来格式变化时用来做兼容判断 |

> `demo` 这个字段之所以在数据里而不是在 README 里：因为"我发的是 demo"和"我发的是能直接跑的东西"这两件事，必须在**代码能判断的地方**分开，否则只能靠人自觉。

## 三、states.json：界面 = 特征

```json
{
  "unknown": {
    "description": "无法识别的界面。引擎的终止条件。",
    "templates": []
  },
  "main_map": {
    "description": "主界面。特征：底部功能栏 + 中央星域。",
    "templates": ["templates/main_map.png"],
    "min_confidence": 0.78
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `description` | 人话描述。写"看到什么能确认是这个界面"，不要写"这是主界面"——后者没信息 |
| `templates` | 相对本包目录的图片路径。**裁最小必要区域**，不要把整屏当模板 |
| `min_confidence` | 匹配阈值，默认 0.75 左右。动画帧、渐变、半透明遮罩要适当调低 |

三条规则：

1. **`unknown` 必须存在**，且它的 `templates` 必须是空数组。它是终止条件，不是兜底状态。
2. **模板图裁小不裁大**。整屏模板对分辨率、UI 缩放、语言都敏感；裁到"只有这个界面才有的一小块结构"（标题栏、特定的按钮排列、独有的图标组合），跨设备的稳定性高一个量级。
3. **不要把动画中间帧当模板**。选一张稳定停留超过 1 秒的画面。

## 四、goals.json：目标 = 步骤序列

```json
{
  "look_main": {
    "description": "确认当前是否在主界面。只读。",
    "requires_state": "any",
    "steps": [{"skill": "assert_main"}],
    "on_fail": "abort",
    "max_attempts": 1
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `description` | 这个目标解决什么问题。模型会读这句来决定要不要选它，所以要写清楚"什么时候该用" |
| `requires_state` | 必须在哪个界面开始。`"any"` 表示不限制 |
| `steps` | 技能名序列，可带 `args` |
| `on_fail` | `abort`（默认）或 `retry_once` |
| `max_attempts` | 最小 1 |

目标层不写动作细节。目标说的是"去舰队面板"，技能说的是"点哪个元素、等多久"。混在一起写，换一个界面布局就得改目标，而不只是改技能。

## 五、skills.json：技能 = 原子动作

```json
{
  "assert_main": {
    "description": "断言当前在主界面",
    "pre_states": ["any"],
    "steps": [{"op": "assert", "state": "main_map"}],
    "expect_state": "main_map",
    "timeout_ms": 10000,
    "retryable": true
  }
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `steps` | 是 | 非空。至少一步 |
| `expect_state` | 是 | 执行完应该在什么界面。**不能是 `unknown`**（见下） |
| `pre_states` | 否 | 允许的前置界面，默认 `["any"]` |
| `timeout_ms` | 否 | 默认 30000 |
| `retryable` | 否 | 默认 true。涉及确认、消耗、购买的必须设为 `false` |

### 允许的 step 形态

| op | 参数 | 说明 |
| --- | --- | --- |
| `tap` | `target` | 按**元素名**点击，由 agent 现场定位 |
| `wait` | `ms` | 死等。能不用就不用，改用 `wait_for` |
| `wait_for` | `state`, `timeout_ms` | 等到某个界面出现 |
| `swipe` | `target_from`, `target_to`, `duration_ms` | 按元素名滑动 |
| `key` | `name`（如 `back`） | 按键 |
| `assert` | `state` | 断言界面。不改状态，只验证 |

`tap` 的 `target` 是**元素名**，不是坐标、不是路径、不是百分比。元素名由 agent 在自己的模板/配置里映射到真实像素位置——这一步必须在能看到真实屏幕的机器上做。

### 为什么 `expect_state` 不能是 `unknown`

`unknown` 的含义是"我不知道现在是什么"。把它当期望结果，等于允许"不知道也算成功"。这个口子一开，所有识别失败都会变成"成功"，熔断和终止逻辑全部失效。

所以加载期就拒绝。报错会直接说清原因。

## 六、三条硬约束（`tools/selftest.py` 逐条检查）

### 约束一：包内不许出现坐标或几何字段

被拒的键名（大小写不敏感）：`x` `y` `px` `py` `coord` `coords` `coordinate` `coordinates` `bbox` `box` `point` `position` `pos` `offset` `left` `top` `width` `height` `x_pct` `y_pct`。

宽高也禁，是因为适配包里出现 `width`/`height` 通常意味着有人在描述"按钮在这块区域"——那就是绝对几何，换分辨率就错。

报错会明确指出"哪个文件、哪个键、为什么不允许"。

### 约束二：`unknown` 是终止条件

- `states.json` 里必须定义 `unknown`
- 引擎在任何时候识别为 `unknown`，立即终止当次执行，**不重试、不换下一个技能、不"大概是主界面吧"**
- 技能 `expect_state` 不能是 `unknown`
- 目标 `requires_state` 写 `unknown` 无意义，会被忽略

这条约束是"失败即停"的具体实现。它让最坏情况变成"什么都没做"，而不是"在错误的界面上做了点什么"。

### 约束三：配置里没有坐标块

`config.toml` 里任何键名含 `coord`/`x`/`y`/`bbox` 之类的字段都会被拒绝加载。老版本有过 `[coordinates]`，v0.2 起删掉了；如果从旧配置复制，会直接报错而不是静默忽略——沉默接受会让人以为坐标准了。

## 七、demo 级包的定义

"demo 级"不是形容词，是三条可检查的具体规则：

1. `manifest.json` 里 `demo: true`
2. `skills.json` 里所有 step 的 `op` 只能是 `assert` 或 `wait_for`
3. 模板图是自己绘制的结构示意（黑白线框、色块示意均可），**不是游戏截图**

满足这三条，插件会：

- 允许演练执行（截图、识别、报"本来会做什么"）
- **拒绝实跑**，即使四道门全过。错误信息写的是"demo 包只能演练"，不是"配置错误"

demo 包的价值在链路验证，不在好用。它让你在承担零风险的前提下确认"我的 agent 通了、模板匹配能认出东西、命令能跑通"。

## 八、社区提交：边界写在这里

**总规则一句话**：社区共建只收 **demo 级 / 教学性质** 的适配包，不收可直接使用的完整自动化脚本。

这条规则不是"暂时这样"，是项目的定位。理由在下面表格里逐条写了，但先说清最核心的一条：

> 一个能直接跑起来的完整游戏脚本，和一份描述"怎样描述界面"的格式示例，是两种完全不同的东西。
> 前者发出来，这个项目就变成了"外挂分发站"；后者发出来，它还是个工具框架。
> 这条线一旦模糊，后面所有的安全设计都不会有人再当真。

### "教学性质"的具体含义

不是"看起来比较简单"，而是能通过这三个问题的检查：

1. **它是否以说明为目的？** 包里有没有注释、README 说清"这一步在演示什么"。
2. **它是否可被替换成别的游戏？** 教学包的结构应当能让人照着改出自己的包；如果一个包只对某一个游戏有意义、且换个游戏就完全无用，它更接近"成品"而非"示例"。
3. **去掉模板图之后它还成立吗？** 教学包的骨架（界面划分、状态流转）应当独立于具体美术资源。绑死在某套截图上的包，换个版本就废，也没有教学价值。

### 接受的

| 类型 | 要求 |
| --- | --- |
| 自己的适配包（demo 级） | 满足上面第七节三条；跑过 `python tools/selftest.py` |
| 识别思路改进 | 说明在什么分辨率/缩放/语言下原方案失效 |
| 文档修正、错别字、翻译 | 直接提 |
| 引擎 bug、边界情况 | 附 `trace` 或复现步骤（脱敏后再发） |

### 不接受的

| 类型 | 原因 |
| --- | --- |
| 含完整可运行操作序列的包（`tap`/`swipe`/`key` 齐全） | 这已经不是"格式示例"，是可直接使用的自动化脚本。分发它会把项目性质改掉 |
| 含游戏原始美术素材的模板图 | 版权问题，且会误导人以为"模板就该长这样"，而那个"这样"绑死在某个版本上 |
| 绕过检测、反作弊、设备指纹伪装相关内容 | 不做，也不讨论 |
| 多开、批量刷资源、账号交易相关 | 同上 |
| 只发一个 zip 没有说明的 | 无法审。至少要说清适用于哪个游戏/分辨率/语言 |
| 把完整脚本改个名字叫 "demo" 的 | `demo: true` 会被插件在运行时校验（step 只能是 assert/wait_for），改名没用。想绕这条规则的人通常也会被其他规则挡住，所以这里不必再加人工审查 |

### 提交前自检

```bash
python tools/selftest.py    # 会检查包结构、坐标字段、demo 只读性
```

如果它红了，先修到绿。它红的原因通常就是审包时会拒的原因。

### 许可

- 插件本体：MIT
- 你的适配包：你自己定，但请在 `manifest.json` 的 `license` 里写明。没写的话默认按"仅允许本地使用、不随插件再分发"理解。

## 九、常见错误对照

| 报错 | 原因 | 怎么改 |
| --- | --- | --- |
| `适配包被拒绝：... 出现坐标字段 x` | 写了 `{"x": 320, "y": 480}` | 改成 `{"target": "confirm_button"}`，由 agent 定位 |
| `技能 xxx 没有声明 expect_state` | 缺字段 | 补上执行完应该在的界面 |
| `技能 xxx 的 expect_state 不能是 unknown` | 把"不知道"当期望 | 换成具体界面；如果真不知道，说明这个技能设计有问题 |
| `技能名 \`Xxx\` 不合法` | 有大写/空格 | 改成小写+下划线 |
| `pack_id 与目录名不一致` | 复制目录后忘了改 | 两处统一 |
| `目标 xxx 没有 steps` | 空目标 | 至少引用一个技能 |
| `适配包 ... 顶层必须是对象` | JSON 是数组 | 单个包是对象，不是数组 |
| 加载成功但一直 `unknown` | 模板图太大/太依赖美术/分辨率变了 | 裁小模板、降低 `min_confidence`、跑一次校准 |

## 十、一个最小的可用包长什么样

如果你只想验证链路，不需要写任何新东西——仓库自带的 `demo` 包就是这个最小形态：4 个界面、3 个只读目标、4 张手绘线框模板。

想加自己的游戏，从复制 `demo/` 开始，改 `pack_id`、换模板图、把 `demo` 改成 `false`，然后一步一步加技能。第一步永远建议是 `assert`：先确认"我能认出这个界面"，再谈"我要点它"。
