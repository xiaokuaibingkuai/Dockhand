# 项目备忘：已定的事，以及为什么这么定

这份文件记录**已经定下来的决策**，不是待办清单。

写它的原因：这类决策在半年后回头看时，最容易被"再优化一下"推翻。而推翻它们通常不是因为想得更清楚了，只是因为忘了当初为什么这么定。所以每一节都写清三件事：**定了什么、为什么、什么情况下才该改**。

日期以 `0.2.0` 为基准。

---

## 一、包 B 只发 demo pack，社区共建只收 demo 级 / 教学级

**定了什么**

- 包 A（`engine/`）：通用引擎，MIT，正常开源。
- 包 B（`game_adapter/`）：只发 `demo` 一个包，且它是只读示例——4 个界面、3 个只读目标、4 张手绘线框模板。
- 社区提交：只收 demo 级或教学性质的适配包。不收含完整 `tap`/`swipe`/`key` 序列的成品脚本。

**为什么**

包 B 才是"能操作某个具体游戏"的那部分。发一个完整的包，等于把这个项目从"工具框架"变成"某个游戏的外挂"，两件事的后果完全不同：

| | 只发 demo | 发完整包 |
| --- | --- | --- |
| 项目性质 | 自动化框架 + 格式规范 | 具体游戏的外挂 |
| 谁承担风险 | 使用者自己写包，自己判断 | 分发者 |
| 素材版权 | 线框图，无争议 | 游戏截图，有争议 |
| 游戏更新后 | 不影响 | 包失效，需要持续维护 |
| 别人拿去做什么 | 得自己写，有门槛 | 开箱即用，无门槛 |

最后一行的差别最关键：**门槛本身就是一层保护**。它让"随手拿去刷资源"这件事变得不那么随手。

**什么情况下才该改**

只有当以下三条同时成立时才该重新讨论：

1. 项目已经有稳定的用户群，且多数人卡在"写不出第一个包"这一步（有数据，不是猜测）；
2. 有办法在不分发完整包的前提下降低这个门槛（例如交互式包生成器）；
3. 你对"这个项目被用来做什么"的预期发生了变化，并且愿意承担随之而来的责任。

只是"有人想要"不构成理由。有人想要，和该不该给，是两件事。

## 二、不做主动通知游戏厂商，只做被动预案

**定了什么**

- **不**主动联系任何游戏厂商申请许可、报备、或询问"是否允许"。
- 被动预案：留一个专用邮箱。收到下架/停止请求，立即下架，不对抗、不辩论。

**为什么不做主动通知**

这个决定违反直觉（"主动沟通不是更负责吗"），所以要写清理由：

1. **主动去问，拿到的答复几乎必然是"不允许"。** 没有哪家厂商的法务会为一个自动化工具开书面许可。而一旦拿到一份"不允许"的书面答复，之后再分发就从"可能不被允许"变成"明确知道不被允许还继续分发"。
2. **主动联系会留下书面记录**，记录的是"制作者知道这事有争议"。这在任何后续纠纷里都不是有利证据。
3. **厂商的沉默不等于许可，但也不等于拒绝。** 现实里绝大多数此类工具的状态是"没人管"。主动去问，等于把一个"没人管"的状态变成"被明确拒绝过的状态"。
4. 这个项目不靠"厂商支持"活着，它靠"用户自己承担风险"活着。把责任讲清楚（免责声明），比争取一个多半拿不到的许可更实际。

**为什么要有被动预案**

因为"不主动联系"不等于"不回应"。留一个邮箱、收到请求就下架，意味着：

- 如果有人真的介意，有一个明确、低成本的途径表达；
- 回应方式是"照做"，不是辩论——辩论只会把事情变大；
- 这个姿态本身是诚实的：我没去要许可，但你要我停，我就停。

**什么情况下才该改**

- 收到正式的法律函件（此时不是"要不要联系"的问题，是"怎么应对"的问题）；
- 项目被某个平台正式接纳（例如上架某个有审核机制的应用市场），平台的规则会取代这条。

## 三、专用联系邮箱

**定了什么**

对外只用一个专用邮箱，不用个人常用邮箱。当前使用：

```
bingkuaiovo@126.com
```

**为什么单独开一个**

1. 这类项目的来信可能包含不友好的内容。专用邮箱被弃用、注销的代价，远小于个人邮箱被淹没。
2. 便于"彻底退出"：如果哪天决定不做了，注销一个邮箱就是干净的下架——不需要解释，也不需要逐个回复。
3. 便于交接：一个邮箱可以交给别人，个人邮箱不行。

**放在哪**

只用在这几处，**不写进代码**：

- `README.md` 的联系方式段
- `SECURITY.md` 的安全问题报告入口
- `docs/适配包格式.md` 的提交说明

代码里硬编码邮箱的坏处是：换地址要改代码、发版。而这类信息本来就该是文档级的。

**什么情况下才该改**

邮箱地址本身就是发布前必须替换的占位项，见下节清单。

## 四、暂停热键：如实标注"未验证"

**定了什么**

`/ship status` 显示 `暂停热键：F12（未验证）`，而不是 `已配置`。

**为什么**

插件只能检查配置里填没填，无法验证这个键在电脑侧 agent 上真的注册成功、真的按得停。

"以为有急停、按下去没反应"是最坏的情况——出事时人会因为信任它而多等几秒。诚实地说明一个保护措施的边界，比让它看起来完整重要。

**什么情况下才该改**

当 agent 侧提供一个"热键自检"接口（例如 `/v2/selftest_hotkey` 让用户按一下、agent 回报收到），并能验证注册成功时，才可以显示"已验证"。

## 五、免责确认持久化到本地标记文件

**定了什么**

`/ship accept` 写 `disclaimer_accepted.json` 到插件数据目录，与配置项的 `disclaimer_accepted` 取"或"。

**为什么不用配置**

插件配置的写入能力在不同 SDK 小版本里不统一（有的有 `ctx.config.set`，有的没有）。指望"发一句命令就帮你改配置"会在一部分环境里静默失败——而失败的表现是"我明明确认过了，重启又让我确认"。

本地标记文件不依赖任何框架能力，读坏了也只退回"未确认"，不会让插件加载失败。

**什么情况下才该改**

当 SDK 提供稳定的配置写入能力，并且有明确的"配置已保存"回执时，可以改为只写配置。在那之前，两份来源并存不是冗余，是兼容。

## 七、这些决定之间的关系

```
包 B 只发 demo ──┬─→ 适配包格式文档的"提交边界"必须写死
                 └─→ demo 模板必须是重绘线框（不能是截图）

不做主动通知 ────┬─→ 必须有被动预案（专用邮箱）
                 └─→ 免责声明必须写明"自行确认游戏条款"

demand 门槛 ─────→ 演练模式必须是默认（否则新手第一次就真跑）

热键未验证 ──────→ 状态显示必须如实（不能显示"已配置"）
```

这不是六个独立的选择，是同一套判断在六个地方的表现：**默认保守、边界清晰、把判断权交回用户、不假装自己更安全。**
