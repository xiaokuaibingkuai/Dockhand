# 安全说明

## 报告问题

`bingkuaiovo@126.com`

> 安全报告请发到上面的邮箱，或在 https://github.com/xiaokuaibingkuai/Dockhand/issues 提交。
> 单独开一个邮箱而不是用私人邮箱，理由在备忘第三节：这类项目的来信未必都友好，弃用一个专用邮箱的代价远小于被淹没。

**请只报告本插件自身的代码问题**，例如：

- 能绕过演练模式（本该只演练却真的点了）
- 能绕过四道门直接实跑
- 诊断包脱敏不干净（把令牌、设备序列号、真实截图漏了出去）
- 适配包校验可被绕过（例如用别名让非 demo 包冒充 demo）

**不要报告**：

- 游戏本身的漏洞、反作弊机制细节——这个项目不碰这些，也不讨论
- "怎么让它多开/更快刷"——不是安全问题，是方向问题，答案是不会做
- 某个具体游戏适不适合自动化——请自行确认游戏条款

## 已知的边界（这些不是漏洞，是设计）

说清楚，省得互相浪费时间：

1. **暂停热键无法被插件验证。** 插件只能检查配置里填没填，检查不了那个键在电脑侧真的注册成功、真的按得停。`/ship status` 显示"（未验证）"就是实话。如果你需要一个自己验证过、能确认生效的急停手段，请自行测试，别依赖默认值。

2. **演练模式不发送输入事件，但会截图。** `/ship observe` 和演练执行都会向电脑侧请求截图。截图留在电脑侧 agent 手里，插件只拿识别结果 + 诊断时才会取（且脱敏）。

3. **"拒绝实跑"不等于"没有风险"。** 四道门拦住的是插件自己发起执行；它拦不住你在电脑侧手动操作，也拦不住别的程序操作那台设备。

4. **适配包是数据，能做的不只是断言。** 一个非 demo 包如果带 `tap` 步骤，加载就会执行这些步骤。**只加载你自己写或你审过的包**——格式文档里的校验能拦住明显的错，拦不住"看起来没问题但意图不良"的包。这是数据驱动架构固有的信任边界。

5. **不涉及检测规避。** 不伪造设备指纹、不隐藏 adb 连接、不改游戏内存。这些是刻意的边界，不是能力不足。

## 令牌与凭据

- 插件与电脑侧 agent 之间的令牌由你来定，走 HTTP 头传递，不落盘到插件数据目录。
- 诊断包里令牌会被替换成固定占位串再打包。
- 仓库里不放任何真实令牌。`config.example.toml` 里是 `""`。
